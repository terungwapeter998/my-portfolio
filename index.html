I started noticing something early on: the software holding up critical operations in Africa kept breaking. Payments failing. Records corrupting. Systems going down at the worst possible time. That's what pulled me toward systems engineering. Not as a career choice. As a problem I couldn't stop thinking about.

My Electrical and Electronic Engineering taught me to think in physical constraints and control loops. That discipline followed me through my B.Sc. in Computer Science at ABU Zaria, where I started applying the same thinking to software. The result was what I now call Logical Determinism: the same inputs always produce the same outputs. No surprises. No silent failures.

I started Milês Platforms Group because I got tired of watching institutions settle for systems that weren't built to last. In our economy, a system failure isn't just a technical glitch. It stops operations, corrupts records, breaks trust with clients and regulators. That's not acceptable.

Most software shops move fast and patch problems after the fact. We don't work that way, We don't move fast, We move Correctly. Every system we build starts with architecture. Clean domain boundaries, append-only ledgers, isolated logic. The result is software that doesn't develop mystery bugs six months after launch.

We assume the environment will misbehave. Networks drop. Clients send garbage data. Third-party APIs go offline. Our systems are designed to not care. The internal state stays correct regardless. That's what Bounded Determinism means in practice.

Core Philosophy

Seven pillars.
One standard.

These aren't preferences or best practices. They're the non-negotiables that every system I build has to satisfy. All seven. No exceptions.

Pillar I

Architecture / Infrastructure Singularity

The business logic lives in one place. The infrastructure that runs it lives somewhere else. They don't mix. External drift in one doesn't corrupt the other.

Pillar II

Hexagonal Architecture (Ports & Adapters)

Core logic sits behind ports. Adapters connect it to the outside world. The result: you can test everything in isolation, swap out frameworks, and the business rules stay untouched.

Pillar III

Deterministic Ledger

Nothing gets overwritten. Every transaction goes through a sequential, append-only log. You can trace any record back to its original state, in order.

Pillar IV

High-Integrity Engineering

"Move fast and break things" doesn't work when your client is a hospital or a school. Correctness isn't a feature. It's the baseline.

Pillar V

Logical Determinism

Same inputs. Same outputs. Every time. No hidden state, no unexpected side effects, no failures that only show up in production under load.

Pillar VI

System Invariants

Some truths about a system must never change. I define those explicitly and enforce them at every execution path. No transaction can violate them.

Pillar VII

Bounded Determinism

The core state machine has walls. What happens outside those walls, network failures, flaky APIs, bad client requests, doesn't affect what happens inside. The internal state does what it's supposed to do. Always.

Milês SchoolDesk

Schools in West Africa are running critical records on fragile systems. Student histories getting corrupted. Financial records that can't be audited. Grading data that changes when it shouldn't. SchoolDesk fixes all of that.

Every administrative action goes through an explicit input port. The school's history is append-only. You can verify any record at any point in time. It doesn't get overwritten. It doesn't drift.

Immutable Student Records
Academic records are sealed on creation. Nobody can quietly change a grade or an enrollment record. Every change has a timestamp and an audit trail.
Financial Audit Ledger
Financial records don't get edited. They get appended. Every fee payment and disbursement has an immutable entry in the ledger.
Deterministic Grading Engine
Run the grade calculation today. Run it again in three years on the same data. You get the same result. No drift, no ambiguity.
Hexagonal Admin Core
The school's core logic is separate from the infrastructure running it. You can test enrollment rules, grading logic, and financial calculations independently. Nothing is tangled together.
